
# Job Seiri データ構造化 & ルール設計案（v1）

このドキュメントは、Job Seiri における「求人ページの構造化」と「ルールベース抽出＋LLM最小利用」の設計案をまとめたものです。  
実装言語やフレームワークには依存せず、アルゴリズムとデータ構造・フローにフォーカスしています。

---

## 0. ゴールと前提

### ゴール

1. ブラウザ拡張から送られてきた URL・タイトル・テキスト（content）を、**できる限りルールベース／ロジックベース** で構造化する。
2. LLMは「最初から全部やる職人」ではなく、**ルールベースの QA・補正・補完に限定** する。
3. 明らかに求人ではないページ、一覧ページなどは **明示的に判定し、ユーザーにフィードバック** する。
4. 将来的な「履歴書マッチング」や「向いている企業群のレコメンド」の土台になる構造を持つ。

### 前提・制約

- 入力は「ユーザーがブラウザで開いたページ」に限る（クローラーは作らない）。
- 給与や勤務地などは完全精度は求めず、「人間の判断を早くする目安」を優先。
- LLMコストを抑えるため、**ルールベース＋軽い LLM 補正** を基本設計にする。
- 日本語求人が中心だが、外資系サイトなど英語混在もありうる。

## 1. データモデル設計

### 1.1 Job（求人レコード）の基本構造

```ts
Job {
  id: string;
  url: string;
  title: string;
  content: string;        // 抽出したテキスト（最大 N 文字）
  sourceHost: string;     // 例: "herp.careers", "www.company.co.jp"

  createdAt: Date;

  // 状態管理（キープ or アーカイブ）
  isPinned: boolean;      // キープ（あとで読む・応募検討）
  isArchived: boolean;    // アーカイブ（今回は捨てる）

  // ページ種別 & 解析メタ情報
  pageType: "job_detail" | "job_list" | "non_job" | "unknown";
  parseVersion: string;   // ルールセットのバージョン (e.g. "v1.0")
  parseConfidence: number; // 0〜1 の自信度（ルール側で雑に決める）
  parseIssues: string[];   // 何か怪しいときの警告メッセージ（例: "Looks like a listing page"）

  // 構造化フィールド（ルールベース＋必要に応じて LLM 補正）
  companyName: string | null;
  jobTitle: string | null;       // 職種名（title とは別に、Job上の正式名称）
  employmentType: "full_time" | "contract" | "temporary" | "intern" | "other" | null;

  salaryMin: number | null;      // 円ベース
  salaryMax: number | null;
  salaryBand: "〜500" | "500-700" | "700-900" | "900+" | null;

  locationText: string | null;   // 「勤務地」欄の生テキスト
  remoteType: "onsite" | "hybrid" | "remote" | "unknown";

  jobType: string | null;        // "営業" "CS" "コンサル" "PdM" などのカテゴリ
  industry: string | null;       // "SaaS" "HR" "Fintech" "Consulting" など

  requiredYears: number | null;  // 「n年以上」をざっくり抽出
  seniorityLevel: "junior" | "mid" | "senior" | "manager" | null;

  // 将来の AI マッチング用
  aiMatchScore: number | null;   // 履歴書とのマッチ度（0〜100）
  aiMatchComment: string | null; // なぜそう判断したかのコメント

  // ユーザー入力
  userNote: string | null;
  userRating: number | null;     // 0〜5 などの主観評価
}
```

### 1.2 生データ保存の方針

- 可能なら `rawHtml`（フル）は保存せず、`content` として「テキスト化された本文」だけ持つ。
- ただし将来 LLM で再解析したい場合は、**別のストレージに rawHtml を置いておく選択肢もあり**。
- バージョン管理のため、`parseVersion` を必ず更新する。

---

## 2. 処理フロー全体像

1. 拡張機能 → `POST /jobs/capture` に `{ url, title, content }` を送信。
2. サーバ側で `Job` レコードを初期作成：
   - `sourceHost` 抽出
   - `isPinned = false`, `isArchived = false`
   - `pageType = "unknown"`
3. 「解析キュー」に投入し、以下を実行：
   1. ページ種別判定（job_detail / job_list / non_job）
   2. 構造化フィールドのルールベース抽出
   3. parseConfidence / parseIssues のセット
4. 後続で（必要な場合のみ）LLM QA バッチをかける。

## 3. ページ種別判定ロジック

### 3.1 基本アイデア

- 「求人詳細ページ」「求人一覧ページ」「求人以外」の 3 種類をざっくり判定する。
- 拡張機能はどこでも押せてしまう想定なので、**サーバ側で「これは求人じゃない」と弾く** のが重要。

### 3.2 判定用の特徴量（ヒューリスティック）

以下はすべて content（テキスト）ベースで考える。

#### (A) 求人らしさのポジティブ指標

- 「募集要項」「仕事内容」「応募資格」「勤務地」「給与」「勤務時間」といったセクション見出しが複数存在。
- 「応募する」「エントリー」「この求人に応募」「Apply」などのボタン文言が存在。
- 「年収」「想定年収」「月給」「賞与」等の給与関連ワードが複数出る。
- 「必須要件」「歓迎要件」「必須スキル」「歓迎スキル」などの項目がある。

#### (B) 一覧っぽさの指標

- 同じパターン（「職種名 + 会社名 + 勤務地」）が複数回繰り返されている。
- 「件中」「〇件の求人」「検索結果」といった文言。
- 「次へ」「前へ」「1 2 3 …」などページング要素。

#### (C) 非求人ページの指標

- 「会社概要」「IR情報」「お問い合わせ」「プライバシーポリシー」などのみが主要。
- 一切「応募」「募集」「年収/給与」などが出てこない。
- 重複したリンクの羅列が大半（ナビゲーション中心）。

### 3.3 判定アルゴリズム案（スコアリング）

1. 各特徴に対してスコアを付与：
   - job_detail_score（最大 10 点くらい）
   - job_list_score
   - non_job_score

2. 例）  
   - 「募集要項」「応募資格」「勤務地」「給与」などの見出しを含む → job_detail_score +2 ずつ  
   - 「〇件の求人」「検索結果」 → job_list_score +3  
   - 「この求人に応募」 → job_detail_score +3  
   - 「IR情報」「決算短信」「プレスリリース」ばかり → non_job_score +3

3. 最終判定：  
   - max スコアが 3 未満 → pageType = "unknown"  
   - job_detail_score が最も高く十分な値 → "job_detail"  
   - job_list_score が圧倒的に高い → "job_list"  
   - non_job_score が高く、job_detail_score が低い → "non_job"

4. `parseConfidence` は、max スコアを適当に 0〜1 に正規化して使う。

### 3.4 ユーザーへのフィードバック

- `pageType === "job_list"` の場合：  
  → UI 上で「これは求人一覧ページのようです。個別の求人詳細を開いてから保存してください。」などの表示。  
  → isPinned にはしないが、ログとして残しておくかは設計次第。

- `pageType === "non_job"` の場合：  
  → デフォルトで isArchived = true にしておく、または一覧に表示しない。  
  → 「求人ページではないため無視しました」と通知してもよい。

## 4. フィールド別ルールベース抽出
（LLMなしのロジック）

ここでは「ボロボロミスしつつも、おおむね当たる」ラインを狙う。  
給与などミスが怖い項目は、**コンテキストを限定して抽出** することで誤検出を減らす。

### 4.1 共通方針

- すべて content（テキスト）に対して行う。
- 「対象セクションの特定 → その中だけ見て抽出」という 2 段構成にすることで、ノイズ（福利厚生費など）を減らす。
- 抽出結果には internal な confidence を持たせておくと、後で LLM QA の対象選別に使える。

#### セクション抽出の基本

- 行単位（改行単位）に分割する。
- 「勤務地」などのキーワードを含む行を見つけ、その前後 N 行（例：±5 行）をそのセクションの候補とする。
- 同様に「給与」「年収」「報酬」「想定年収」等もセクション候補にする。

---

### 4.2 給与：salaryMin / salaryMax / salaryBand

#### ステップ 1：給与セクション候補の抽出

1. 行ごとにスキャンし、以下の単語を含む行をヒットさせる：  
   - 「給与」「年収」「想定年収」「報酬」「賃金」など。
2. ヒットした行の前後数行（例：±4 行）を「給与セクション候補」とする。
3. セクション候補が複数ある場合：
   - 「福利厚生」「交通費」「通勤費」「家賃補助」等が近くに多いセクションは **優先度を下げる**。  
   - 「年収」「月給」などが含まれ、「賞与」「昇給」が併記される典型的な給与説明っぽい部分を優先。

#### ステップ 2：数値抽出

- 万円表記：`/([0-9]{3,4})\s*万/` → ×10,000 円
- 円表記：`/([0-9]{6,7})\s*円/`

ヒットした数値群から、以下のように解釈する：

- "400万〜600万" → [400, 600]  
- "年収 500万円以上" → min=500, max=null → max = min として扱う  
- "想定年収：600万〜900万＋SO" → [600, 900]

#### ステップ 3：ノイズ対策

- セクション内に「交通費」「通勤手当」「福利厚生」「出張手当」などの単語が多い場合、そのセクションのスコアを下げる。
- 単一セクション内で 3 つ以上の数値レンジが出る場合（例：各種手当列挙）、confidence を低くして、`salaryMin/Max` を設定しない or LLM QA 対象に回す。

#### ステップ 4：salaryBand の決定

- salaryMax(または salaryMin) をベースにざっくり帯に落とす：
  - < 5,000,000 → "〜500"
  - 5,000,000〜7,000,000 → "500-700"
  - 7,000,000〜9,000,000 → "700-900"
  - ≥ 9,000,000 → "900+"

---

### 4.3 勤務地 / リモート：locationText / remoteType

#### locationText

- 「勤務地」「就業場所」「勤務場所」「配属先」などを含む行を探す。
- 最初に見つかった行と、その直後 1〜3 行を連結したものを `locationText` に保存。

#### remoteType

- `locationText` と全体 content を対象に、以下の優先順位で判定：

1. "フルリモート" "完全在宅" "全国どこでも" → remote
2. "リモートワーク可" "在宅勤務あり" "ハイブリッド" "一部リモート" → hybrid
3. "原則出社" "出社メイン" "リモート勤務不可" → onsite
4. マッチしない → unknown

---

### 4.4 雇用形態：employmentType

- content 内のキーワードによるルール：

1. "正社員" を含む → full_time
2. "契約社員" → contract
3. "業務委託" "フリーランス" → temporary or other
4. "インターン" → intern
5. なければ null

複数ヒットした場合は、full_time を最優先、それ以外は最初に見つかったもの。

---

### 4.5 職種：jobType

- title + content を対象に辞書マッチ。

例：

- 営業系  
  - "法人営業" "フィールドセールス" "インサイドセールス" "アカウントエグゼクティブ" など → "営業"
- CS系  
  - "カスタマーサクセス" "CSM" "オンボーディング" "カスタマーサポート（B2B寄り）" → "CS"
- コンサル系  
  - "コンサルタント" "DXコンサルタント" "戦略コンサルタント" "ITコンサルタント" → "コンサル"
- プロダクト系  
  - "プロダクトマネージャー" "PdM" "プロダクトオーナー" → "PdM"
- PM/プロジェクト系  
  - "プロジェクトマネージャー" "PM" "PjM" → "PM"
- マーケティング系  
  - "マーケティング" "グロース" "デジタルマーケティング" → "マーケ"

マッチ優先順位：

- title を優先し、なければ content で検索。
- 複数カテゴリにマッチした場合、定義した優先順位リストに従う or "複合" として扱う（実装時に選択）。

---

### 4.6 業種：industry

- sourceHost と content 両方を見る。

例：

- SaaS  
  - "SaaS" "クラウドサービス" "サブスクリプション" "B2B SaaS" → "SaaS"
- HR  
  - "人材紹介" "採用支援" "タレントマネジメント" "HRテック" "適性検査" → "HR"
- Fintech  
  - "キャッシュレス" "決済" "フィンテック" "金融サービス" → "Fintech"
- コンサル  
  - big4 やコンサルファームのドメイン、"戦略コンサルティング" "マネジメントコンサルティング" → "Consulting"
- SIer / インフラ  
  - "SI" "システムインテグレーション" "インフラ構築" "ネットワーク" → "SIer/Infra"

マッチしなければ null。

---

### 4.7 経験年数 / シニアリティ：requiredYears / seniorityLevel

#### requiredYears

- `([0-9]+)\s*年以上` パターンで数値を拾う。
- "社会人経験3年以上" "5年以上のマネジメント経験" 等をすべて集め、最小値を採用。
- 「未経験歓迎」「経験不問」などがある場合は null とする。

#### seniorityLevel

- jobType, requiredYears, content をもとにざっくり判定。

例：

- content に "マネージャー" "リーダー" "責任者" "Head of" など → manager
- requiredYears >= 7 → senior
- requiredYears 3〜6 → mid
- requiredYears 0〜2 or "未経験歓迎" → junior

## 5. LLM の役割と導入ポイント

### 5.1 基本ポリシー

- LLM は **「最後の保険・QA・補正」役** としてのみ使う。
- すべての Job に対して LLM を投げるのではなく、「ルールベースで confidence が低いもの」だけ対象にする。
- LLM には必ず「ルールベースの結果(JSON)」も渡し、**それを尊重して修正／補完させる**。

### 5.2 LLM に渡す情報

- 入力：
  - `content`（または一部抜粋）
  - ルールベースでの抽出結果（JSON）
  - 期待するスキーマ定義（companyName, salaryMin, salaryMax, ...）

- 出力：
  - 同じスキーマの JSON（補正済み）
  - どのフィールドを修正／補完したかのメタ情報（optional）

### 5.3 LLM 適用対象の例

- 給与セクションが複雑すぎてパターンマッチが混乱したケース
- 会社名 / 求人タイトルがヘッダー・フッターに埋もれて抽出できないケース
- 職種・業種が曖昧（複数カテゴリにヒット）で迷うケース

## 6. ユーザー操作とエラーケースの扱い

### 6.1 一覧ページでボタンが押された場合

- pageType 判定で "job_list" と判断された場合：
  - Job レコードは作られても良いが、UI では「一覧ページ」としてラベル。
  - `parseIssues` に `"Looks like a job listing/search result page."` を追加。
  - 一覧表示時に、注意アイコン＋「これは求人一覧ページのようです。個別求人を開いて保存してください。」などと表示。

オプション：

- 完全に無視したい場合は、isArchived = true にして通常ビューから除外する。

### 6.2 明らかに求人ではないページ

- pageType = "non_job" かつ job_detail_score が低い場合：
  - Job レコードを即 isArchived = true にする。
  - ユーザーには軽く通知（必要なら）。
  - 将来的な分析用途に取りたければ、非表示のままデータだけ残すことも可能。

### 6.3 「本来欲しかったものが取れない」系の対策

- できるだけ「1ページ＝1求人」を前提とした設計にする。
- 一覧ページで押されたときには意識的に「一覧ですよ」と返すことで、ユーザーの期待値を調整。
- 一度保存された Job に対して、「このページは求人じゃなかった」とユーザーがマークできる UI を用意し、pageTypeを修正することも考えられる。

---

## 7. 今後の拡張と、今回の設計の位置づけ

- 今回の設計はあくまで **v1 のルールベース構造化＋LLM QA 前提**。
- 将来的には：
  - 履歴書の構造化（同じスキーマへのマッピング）
  - ルールベース＋LLM でのマッチングスコア算出
  - 「壁打ち」結果を構造化して嗜好モデルを作り、Job のスコアリングに反映
- いずれにしても、「Job がある程度きちんと構造化されている」ことが前提になるため、今回のデータモデルとルール設計が土台となる。
